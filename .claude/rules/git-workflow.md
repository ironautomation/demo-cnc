# Git / GitHub 운영 규칙 (상세)

이 저장소의 규칙이다. 이 파일이 Claude가 따르는 기준이다.

## 운영 목적

GitHub는 단순한 소스 저장소가 아니라, **항상 빌드 가능한 상태를 유지하고 문제를 조기에 발견하기 위한 장치**다.
개발자 개인 PC의 환경 차이로 "내 PC에서는 되는데" 상황이 생기는 것을 줄이고, 배포 가능한 소스와 산출물을 명확히 관리한다.

## 작업 흐름

모든 작업은 최신 main을 기준으로 시작한다.

1. main 최신 소스 받기
2. 작업 브랜치 생성
3. 코드 수정
4. 빌드 확인 — Automation Studio 또는 명령줄 빌드(`docs/build-cli.md`)
5. commit / push
6. Pull Request 생성
7. 빌드 결과를 PR 본문에 기재 (자동 빌드는 아직 없음)
8. 리뷰 또는 확인
9. main에 merge

**작업 단위는 작게 나눈다.** 하나의 Pull Request에는 가능하면 하나의 목적만 담는다.

## 브랜치 규칙

```
main
 ├── feature/기능명      # 새 기능 개발
 ├── fix/수정내용        # 버그 수정
 ├── hotfix/긴급수정     # 배포 후 긴급 수정
 └── refactor/구조개선   # 기능 변경 없는 구조 개선
```

- `main`: 안정적인 기준 브랜치. 항상 빌드 가능한 상태로 유지한다.
- 불필요하게 복잡한 브랜치 전략 대신 main + 작업 브랜치 중심으로 단순하게 운영한다.

## Commit 규칙

Commit 메시지는 **한국어**로, 나중에 봐도 어떤 작업인지 알 수 있게 작성한다. 변경 이력은 문제 추적과 배포 이력 확인에 사용된다.

| 좋은 예 | 나쁜 예 |
|---|---|
| `디스펜서 출력용 X20DO8331 모듈 추가 및 DO_Dispenser_Start 매핑` | `수정` |
| `CNC 원점복귀 순서 Z→XY 설정 및 Y축 상한 변경` | `작업중` |
| `컨베이어 센터링 실린더 선택 조건 수정` | `최종` / `진짜최종` |
| `AxisManual 조그 로직 구조 개선` | `이것저것 수정` |

## 리뷰 기준

모든 PR을 무겁게 리뷰할 필요는 없지만, **영향 범위가 큰 변경은 리뷰 후 병합**한다.

리뷰가 필요한 변경:

- 공용 모듈 변경 (`Global.var` / `Global.typ`, 공용 라이브러리)
- 장비 통신 변경 (EtherCAT / 드라이브 DTM, OPC UA)
- 하드웨어·I/O 구성 변경 (`Hardware.hw`, `IoMap.iom`)
- 태스크 구성 변경 (`Cpu.sw`)
- mapp Motion 축·축그룹 설정 변경 (`mappMotion/*`)
- `RETAIN` 변수의 추가·삭제·타입 변경
- 빌드 설정 변경 (`DemoCNC.apj`)
- 배포 관련 변경
- 다른 기능에 영향이 큰 변경

간단한 문구 수정, 로그 수정, 주석 수정은 AS 빌드 성공만 확인되면 바로 merge할 수 있다.

### 리뷰 시 확인 항목

- main에 병합해도 Automation Studio 빌드가 깨지지 않는가?
- 다른 기능에 영향이 없는가?
- 예외 처리와 로그가 필요한 곳에 들어가 있는가?
- 설정 파일, DLL, 라이선스 파일 누락 가능성은 없는가?
- 현장 장비 동작에 영향을 줄 수 있는가?

## 자동 빌드 규칙

자동 빌드는 개인 PC 환경 의존성을 줄이고, main에 깨진 코드가 들어가는 것을 막기 위한 필수 절차다.

> 이 저장소에는 아직 자동 빌드(GitHub Actions)가 없다. 당분간은 작성자가 Automation Studio에서 빌드를 확인하고 PR 본문에 결과를 적는다.

**실행 시점**: Pull Request 생성 시 / main 병합 시 / 매일 정해진 시간

**빌드 실패 시 원칙**

- PR 빌드 실패: PR 작성자가 원인을 확인하고 수정한다.
- **main 빌드 실패: 최우선으로 복구한다.** 팀 전체 기준 브랜치가 깨진 상태이므로 가장 먼저 복구한다.
- Daily Build 실패: 다음 근무일에 우선 확인한다.

## 파일 관리 및 보안 규칙

### Git에 포함하지 않을 파일

- `src/PLC/Temp`, `Binaries`, `Diagnosis` 폴더, `*.set`, `*.isopen` (Automation Studio 빌드 산출물·개인 설정)
- 개인 PC 경로가 들어간 설정 파일
- 로그 파일과 임시 파일
- 대용량 배포 파일
- 비밀번호, 토큰, 인증키, API Key

### 설정 파일 관리

개인 환경에 따라 달라지는 설정 파일은 그대로 commit하지 않는다. 필요한 경우 example 또는 template 파일로 관리한다.

예: `config.template.xml`, `*.example.*`

## 금지 사항

- main 직접 push 금지
- 빌드 실패 상태에서 merge 금지
- `Temp` / `Binaries` / `Diagnosis` 폴더 commit 금지
- 비밀번호, 토큰, 인증키 commit 금지
- 개인 PC 경로가 들어간 설정 파일 commit 금지
- 여러 기능을 하나의 PR에 몰아서 올리기 금지
- 의미 없는 commit 메시지 사용 금지

## 최종 원칙

> main은 항상 빌드 가능해야 한다.
> 작업은 브랜치에서 한다.
> main 반영은 Pull Request로 한다.
> 빌드 실패 시 merge하지 않는다.
> 개인 PC가 아니라 Build PC 기준으로 판단한다 (자동 빌드 도입 전까지는 AS 빌드 결과를 PR에 명시).
> 현장에 영향을 줄 수 있는 변경은 반드시 공유하고 리뷰한다.
