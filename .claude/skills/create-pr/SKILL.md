# Pull Request 생성 절차

Pull Request는 main에 반영하기 전 변경 내용을 공유하고, 자동 빌드와 리뷰를 통해 문제를 미리 발견하기 위한 절차다.

## 1. 사전 확인 — 순서대로 실행

```bash
git status                # 미커밋 변경 확인
git branch --show-current # 현재 브랜치 확인
```

**현재 브랜치가 `main`이면 여기서 멈추고** 사용자에게 알린 뒤, 변경 성격에 맞는 브랜치를 만들어 옮긴다.

| 변경 성격 | 브랜치 |
|---|---|
| 새 기능 | `feature/기능명` |
| 버그 수정 | `fix/수정내용` |
| 배포 후 긴급 수정 | `hotfix/긴급수정` |
| 기능 변경 없는 구조 개선 | `refactor/구조개선` |

## 2. 빌드 확인

push 전에 **빌드가 성공했는지 확인**한다 — Automation Studio에서 빌드하거나 `docs/build-cli.md`의 명령줄 빌드(BR.AS.Build.exe)를 실행한다. 확인되지 않았거나 실패했으면 **PR을 만들지 말고** 원인을 먼저 수정한다.

자동 빌드(GitHub Actions)는 아직 없으므로, 빌드 확인 여부를 PR 본문 "테스트 여부"에 그대로 적는다.

## 3. 작업 단위 점검

diff를 확인해서 **여러 기능이 섞여 있으면 사용자에게 알리고 PR 분리를 제안**한다.
하나의 PR에는 하나의 목적만 담는다.

## 4. Commit

메시지는 **한국어**로, 무엇을 했는지 알 수 있게 쓴다.

```
디스펜서 출력용 X20DO8331 모듈 추가 및 DO_Dispenser_Start 매핑
CNC 원점복귀 순서 Z→XY 설정 및 Y축 상한 변경
컨베이어 센터링 실린더 선택 조건 수정
```

`수정`, `작업중`, `최종` 같은 메시지는 쓰지 않는다.

커밋 전 스테이징 목록에 `src/PLC/Temp`, `Binaries`, `Diagnosis`, `*.set`, `*.isopen`, 로그·임시 파일, 비밀번호·토큰·인증키·API Key,
개인 PC 경로가 들어간 설정 파일이 포함되지 않았는지 확인한다. 있으면 제외하고 사용자에게 알린다.

## 5. PR 본문 작성

아래 네 항목은 **반드시** 포함한다.

```markdown
## 작업 내용
<무엇을 했는지>

## 변경 이유
<왜 필요했는지>

## 테스트 여부
<무엇을 어떻게 확인했는지. 안 했으면 안 했다고 명시>

## 영향 범위
<영향을 받는 모듈·장비·DB·설정. 없으면 "없음">
```

**장비 통신, I/O 매핑, 축 설정, RETAIN 변수, 배포 설정이 바뀐 PR은 영향 범위를 반드시 구체적으로 작성한다.**

PR 제목은 제목만 봐도 변경 내용을 알 수 있게 쓴다.
미완성 작업을 공유해야 하는 경우 Draft PR로 생성한다.

## 6. 리뷰 필요 여부 판단

아래에 하나라도 해당하면 PR 본문에 **리뷰 요청이 필요하다고 명시**하고 사용자에게 알린다.

- 공용 모듈 변경 (`Global.var` / `Global.typ`)
- 장비 통신 변경 (EtherCAT / 드라이브 DTM)
- 하드웨어·I/O 구성 변경 (`Hardware.hw`, `IoMap.iom`)
- 태스크 구성 변경 (`Cpu.sw`)
- mapp Motion 축 설정 변경 (`mappMotion/*`)
- `RETAIN` 변수 추가·삭제·타입 변경
- 빌드 설정 변경 (`DemoCNC.apj`)
- 배포 관련 변경
- 다른 기능에 영향이 큰 변경

문구·로그·주석 수정만이면 AS 빌드 확인 후 바로 merge 가능하다고 안내한다.

## 7. 생성 및 보고

```bash
git push -u origin <브랜치명>
gh pr create --title "<제목>" --body "<본문>"
```

생성 후 사용자에게 다음을 보고한다:

- PR 링크
- 리뷰가 필요한 변경인지 여부와 그 이유
- Automation Studio 빌드 확인 여부 (자동 빌드는 아직 없음)

## 금지

- main에 직접 commit / push 하지 않는다.
- 빌드가 실패한 상태에서 merge하지 않는다. 사용자가 요청해도 빌드 실패 사실을 먼저 알린다.
- 여러 기능을 하나의 PR에 몰아서 올리지 않는다.
